    Gossil development plan

    Gossil is planned as a Rust library and application for versioned agentic project state. It combines Fossil version-control mechanisms with Gest task management, commands and an application programming interface (API). Axum is the Rust web framework for the embedded server and dashboard. The storage boundary uses libsql, a SQLite database implementation. Git owns source code.

    The checkout implements bounded delta creation and application, their gossil vcs diagnostics, and the inherited-test runner. It also composes byte primitives, token escaping, artifact checksums and local transactions. Native storage adds complete empty-root initialization and bounded private content operations. There is no public SQL interface. The artifact parser adds bounded structural parsing of all eight artifact types with an asynchronous selected-engine date provider. The encoder and decoder guides give the current scope and limits.

    The planned public command domains are issue and vcs. The planned ui command starts an embedded Gest/Axum server and opens a browser, while serve runs the server without a browser. The implemented diagnostics are vcs test-delta-apply, vcs test-delta-create and vcs test-delta. A public wiki or forum product is outside the design, but inherited Fossil mechanisms and tests remain internal compatibility obligations.

    The design and acceptance requirements are in the separate local specification at ~/Projects/AIProjectInfra/docs/gossil/README.md. Its linked acceptance page defines the source inventory and the test families required beyond inherited Fossil and Gest tests.

    Development work is tracked in this project’s local Gest task database. The commands below require an installed Gest tool and that local database. A fresh clone does not supply those task records. Follow the installed .agents/skills/gtw/references/gest_codex_workflow.md for the project workflow.

    The product parent task is xyzzowpv, and iteration usytswsv groups its implementation tasks. A leaf is a task with no child tasks. The completed environment task xnuqympy records bootstrap work. Parent tasks stay open until their complete scope passes.

    With Gest installed and the local task database available, run gest task show xyzzowpv from the repository root to inspect the parent. Use gest task show ID for any task ID in the table below. These task records are local workflow data, separate from the product specification.

    The historical composed core is the library’s delta, byte, token and local storage modules and their private composition test.     Every production change starts with focused tests and checks of the callers and tests that depend on the changed behavior. Fresh GPT-6.1 Sol agents review changes independently and challenge assumptions. The installed guide .agents/skills/gtw/references/gest_codex_workflow.md and root AGENTS.md describe the full process in the checkout. Follow that workflow guide for packet dispatch and result validation before using the commands below.

    An agentic target is a Just command that writes a task packet for a fresh agent. The agent returns a result packet, which the parent validates and records. A record identifies the reviewed file tree and the packet’s nonce, a unique identifier. It applies to that content, so edits can require a new check. Use the installed workflow guide above for packet dispatch, result validation and recording. Printing a packet alone does not complete its check.

    The following commands create and check those packets as part of the review workflow. Run the Just commands in this order. just update-docs, just prose, just review, just test-review, then just check on the final tree. The first four targets emit packets for fresh agents. Dispatch each packet, validate the returned result, then run just record TARGET RESULT_FILE before starting the next gate. Replace the capitalized arguments with the target name and saved result path.

    A worktree is a separate checkout that shares Git history with the primary checkout, the original checkout from which it was created.

    Independent writers use physical worktrees. Each needs an owner, absolute path, topic branch and explicit base. Create a worktree with just worktree-new NAME BASE, using an existing branch or commit for BASE. The recipe reads .worktreelink and links the existing ignored .jlog folder from the primary checkout into the new worktree. For an existing worktree, just worktree-sync applies those links. The link does not install tools or share source edits.

    For dependent branches, finish the prerequisite checkpoint before starting work that requires it.

    The public delivery destination is rahuldave/gossil. After the initial accepted checkpoint reaches main, deliver subsequent changes through reviewed pull requests to main. The coordinator owns pushes and GitHub changes. Commits require complete verification and independent review.

    The saved answer docs-publish=yes selects just docs-publish with smalldocs 0.5.12. The workflow runs on main in the public repository, publishes through Just, then builds and deploys the GitHub Pages artifact. Use GitHub Actions as the Pages source.     Extension contracts and remaining work

    The companion specification contains accepted normative Gest, sync and UI contracts and an accepted storage specification. Its full fixture inventory still requires runtime implementation and qualification. Issue revisions, Git-link encodings and annotation descriptors need byte fixtures before durable extension writes begin. Task qvqyvqlt tracks this contract work. Inspect it with gest task show qvqyvqlt in the local Gest project. Do not invent storage or wire formats.

    The private/shared implementation must follow the companion sync contract for dependency closure, transaction identity, authorization, declassification and identical-byte visibility.

    Dependency closure includes every object that a record requires and determines which related objects must travel together. Transaction identity determines how a transaction is identified across replicas. Authorization controls access, while declassification permits private data to become shared under explicit rules. Identical-byte visibility determines access when private and shared objects contain the same bytes. Shared history must restore without private objects. Unsupported required extensions must fail before an operation reports complete success.
