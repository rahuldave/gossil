Development and contributing

Gossil implements byte primitives, structural artifact parsing and bounded local storage. The gossil executable initializes empty repositories, opens native checkouts, adds explicit paths, lists tracked states and implements three delta diagnostics. The CLI calls the library to select immutable path scopes and record the complete private tracked tree. The prepared glob source adds bounded list matching and a repository-free diagnostic, with a focused source checkpoint described below. The generated Rust API describes the public library surface.

The standalone Gest task values converter validates eleven decoded fields. The Gest project values converter validates four canonical project fields. The Gest author values converter validates six canonical author fields. The Gest artifact values converter validates eight canonical artifact fields. The Gest iteration values converter validates nine canonical iteration fields. The Gest tag values converter validates four canonical tag fields.

The Gest note values converter validates seven canonical note fields. The Gest relationship values converter validates eight canonical relationship fields. The Gest entity tag values converter validates four canonical entity tag fields. The Gest iteration task values converter validates four canonical iteration task fields.

All ten converters operate in memory and leave storage integration, raw field admission and the full Gest API to future work.

The Gest model is a copy of the Gest record types and their primitive values. A record that a converter has validated converts into its model record through the From trait.

The task ticket emitter serializes validated task snapshots with caller-supplied native identity, actor and date. The Gest ticket emitter serializes validated artifact and project snapshots in the same way, and the three kinds share one emitter.

The internal modules for strict local records decode local JSON records and charge queries against fixed limits. The metered content methods read and write content through the metered queries, and they admit only the newest catalog. The issue ticket writer is the first production caller of the metered queries and of those methods.

Initialization creates catalog6 without a checkout. The library can register one existing directory and authenticate its registration by ID or exact root. Opening a repository admits exactly zero or one registration and the supported tracking, scope and private recording family, with private issue tickets written before, between or after check-ins. Bound catalog1 creation retains its checkout and private content operations. Catalog6 generic private content writes remain unsupported; its separate recorder writes complete private file trees. Registration changes the database only.

The source CLI combines registration with bounded locator publication and recovery of the exact registration. Working-file materialization remains future work. See native checkout open.

An empty root is a check-in with no files. Private content operations do not extend that public graph. Build this version from source. The implemented modules do not establish full-engine compatibility. Git remains the source-code authority for this project.

Historical results qualify only their recorded source, inputs and environment. The archived delta1 suite tests delta operations with explicit bounds. It does not qualify storage or the full Fossil engine. Linux qualification and clean-clone CI for the current private recording checkpoint remain separate work.

Contributor setup

Install Rust with Cargo through rustup, and install Git, Just, uv and the jlog command recorder. rust-toolchain.toml pins Rust 1.95.0 with clippy, rustfmt and llvm-tools-preview. CI uses the same compiler, so a local just lint gives the same lints as CI. Run rustup toolchain install in the checkout to install that toolchain. Do not set RUSTUP_TOOLCHAIN, because the variable takes the place of the file.

The repository has installed workflow copies under .agents/. Their owning packages are jnterfaces, jnprofile-rust, agent_gest_git_skills and nossaifd under ~/Projects. Use SKILL_PACKAGES_DIR to select another package location.

just setup
just install --check

just setup supplies the pinned Linux Tcl and Fossil references, or checks the existing tools on other hosts, then fetches Cargo dependencies. just install refreshes the saved tool selection from those companion packages. The runner guide describes those prerequisites.

Read AGENTS.md before changing the repository. Follow the installed Gest workflow for task ownership, tag classification, dependency impact and review. Keep reusable tool changes in their owning packages.

Check a change

Use the repository’s Just entry points:

just fmt-check
just lint
just typecheck
just test
just integration
just doctests
just docstring-check
just docs-check
just docs-build

just docs-check checks the site and the API pages. just typecheck runs just rustdoc-check before its own type check. just rustdoc-check builds the rustdoc with private items and fails on each warning. So just typecheck, and just check with it, fails on a broken intra-doc link. A broken intra-doc link is a link in a doc comment that rustdoc cannot resolve to an item.

just test first runs nine focused Python installer controls. Next it runs scripts/check-ci-config.py and the 78 tests of that checker in scripts/test_ci_config.py. Then it runs the Rust unit tests through the installed coverage workflow. just integration uses that Rust coverage workflow. Its reports do not measure Python installer coverage.

The checker reads .config/nextest.toml and the workflows, and does not run cargo. It accepts only the plain forms that Gossil uses, so a form that it cannot judge fails. .config/nextest.toml must have exactly one override, of the profile default. That override may hold only filter, test-group and threads-required = "num-test-threads". Another override placed before it would win, because nextest takes each setting from the first override that matches.

Each term of the filter must be a plain test(NAME) or binary(NAME), with no =, regex or glob. The filter joins its terms with | or or only. It must name test(plan_cli_and_evidence) and binary(conformance), the tests that must run alone.

Each test(NAME) must name a function with the attribute #[test] or #[tokio::test] in src/ or tests/. Each binary(NAME) must name a test target as Cargo.toml names it. A file tests/NAME.rs gives a target with the stem of the file, NAME, unless a [[test]] entry renames it. For example, an entry renames tests/glob.rs to glob_port, so the stem glob does not count. With autotests = false, no stem counts.

nextest accepts, with no message, a test() term that matches no test, so a renamed test would drop out of the filter in silence. The checker catches the renamed test. A test inside a // comment or a /* */ comment does not count, and /* */ comments nest, as in Rust. A test that a Rust string literal writes out does count, because the checker does not parse Rust strings.

The checker reads each workflow, *.yml or *.yaml. Each install script that a workflow fetches from raw.githubusercontent.com, in any letter case, must come over https at a full commit hash. Each time the host appears, the workflow must write out the whole URL, as https://raw.githubusercontent.com/OWNER/REPO/HASH/. So a URL that takes its ref from a variable or an expression fails.

Each step must be under a job line that is a plain name at an indent of two spaces, below the line jobs:. Each item of a list must be - KEY: or - VALUE, with one space after the dash, so a step in another form fails. Each line that names actions/cache, in any letter case, must be a bare uses: actions/cache@vN, uses: actions/cache/restore@vN or uses: actions/cache/save@vN, with no quotes and no comment.

In each job with a cache step, the step with the id rust must come before the cache steps. It must have no if: condition and no continue-on-error:, and it must write the runner image to its outputs. The line that writes the image must come right after the line that fails the step when the runner gives no ImageOS. Each cache step needs a line that holds only with:, and exactly one line key:. No line of the step may hold a comment.

Each key: and each line of a restore-keys: | block must hold ${{ steps.rust.outputs.image }}. The checker finds the lines of that block by their indent. The save step may instead reuse the primary key of an earlier restore step with the id rust-cache in its job.

Last, the checker checks the release workflow. The workflow must restore the cache, and it may have no defaults: or working-directory: line. The workflow must also remove the coverage stamp of each restored cache. The coverage stamp is the file target/llvm-cov-target/jnprofile-rust-build.txt. A step that holds only a name and run: must remove it. That step must come after each restore, and before the next restore or step that runs just in the same job.

The checker counts a step as one that runs just when the word just appears anywhere in its run line. The word counts even in quotes or after a path.

With JNPROFILE_RUST_NEXTEST=1 set, just integration runs its tests through cargo llvm-cov nextest, which runs several test binaries at once. The job check of the release workflow sets the variable. That mode needs nextest, which cargo install cargo-nextest --locked installs. .config/nextest.toml names the tests that must run alone, with no other test beside them.

In a fix round, run just quick and just integration-changed. just quick runs the format check, clippy, cargo check and the unit tests, with no coverage. just integration-changed runs only the test targets that the change may break, with no coverage. Run the full just check once, on the final staged tree. After a release, just install-bin builds the release binaries into ~/.cargo/bin.

Keep failed, blocked, skipped and disabled-feature observations distinct from passes. Installed tool copies and hook files do not prove actual executions. Complete the required checks and independent review before delivery to main.

Maintain the bundled provider

The root Cargo patch selects the complete libsql-ffi 0.10.0 archive under vendor/libsql-ffi. The root dependency and lockfile also pin libsql and libsql-sys to 0.10.0. The Rust wrapper uses the full Git revision in the TEXT retrieval guide; libsql-sys retains its registry identity. The wrapper correction preserves complete valid TEXT without changing the bundled provider. Its adapted date conversion includes <stdint.h> itself because it uses UINT64_C. The upstream build script does not define HAVE_STDINT_H or HAVE_INTTYPES_H for the core build.

Use these checks when changing the provider:

just libsql-vendor-check
just libsql-vendor-test
just libsql-provider-compile
just libsql-provider-dates
cargo test --locked --test libsql_connection_lifecycle

The compile controls build the complete adapted C source and check version 2 of the write-ahead log (WAL) interface, including xSavepointForget. The core build keeps both optional integer-header defines unset. Linux controls retain the historical 0.9.30 missing-header failure and test the current integer-header requirement. macOS skips those two negative controls because its headers supply the macro. A separate negative control removes <math.h> before the date conversion code.

The lifecycle tests check connection destruction, retained handles and database isolation. They do not establish memory safety through allocator or sanitizer diagnostics. The date recipe runs the retained finite date tests through the bundled Rust provider without coverage instrumentation.

The existing required PR job check / ci runs these compile and semantic checks on Ubuntu 24.04, then builds the site and Rust API with just docs-build. A successful local macOS run does not establish a Linux pass or a Pages deployment.

For regeneration, supply the pinned original registry source and native Fossil source to scripts/regenerate-libsql.py ORIGINAL NATIVE NEW_OUTPUT. The script verifies both input hashes, all seven patch hunks and the output hash. Keep canonical baselines unchanged. Review the source diff before updating the adapted patch, source identity and affected manifest receipts together. The provenance record is evidence/libsql-provider/provenance.json.

The seven hunks do not count semantic adaptations. The mapping in evidence/libsql-provider/upgrade-0.10/adaptation-map.json accounts for all eight old hunks. SQLite 3.47.0 already includes the negative Gregorian century fix. The signed-year change retains the official floor and timezone control flow. Earlier provider reports describe 0.9.30 and do not qualify the upgraded provider.

Shared value validation

All ten converters of Gest values share the private field validators of gest_value_validation. The validators parse identifiers and entity types with the primitives of the Gest model, and the converters parse each status and type the same way. Changes must preserve public conversion behavior and the original parser errors returned through the public error accessor. Before the converters plan the size of the output, they allocate only the short identifier, status and timestamp strings. The title, description and metadata of a task remain borrowed.

The gest_value_validation module also defines the borrowed canonical values that the task, artifact and project ticket emitters serialize. The task emitter writes the status form that gest_task_values defines. It writes the identifiers and the UTC timestamps in the forms that canonical_id and canonical_timestamp define in gest_value_validation.

Historical task-value source mappings and run accounting are preserved in the task value evidence archive.

Native repository CLI

The source routes gossil and gos, vcs and v, and init and new to the checkout-free native initializer. It accepts administrator, date and SHA1 options and uses SQLite randomness in a private memory database. Login fallback uses environment values without a preference database. Existing delta diagnostics retain their dispatcher and argument contracts.

Before dispatch, the product entry answers help requests with the text of the private product::help module, and rejects unknown groups and commands with status 2. The help section gives the forms, and tests/cli_help.rs holds the CLI controls.

The issue group, or i, routes each Gest command by the issue table of product::help. The parser in product::issue checks the command names and their aliases. It runs init, task create, task list and task show, and refuses each other recognised command with status 69. The issue section gives the forms and errors, and tests/issue_cli.rs holds the controls.

product::issue_init runs issue init, and tests/issue_init_cli.rs holds its controls. product::issue_task runs issue task create, and tests/issue_task_cli.rs holds its controls. The handlers of task list and task show are in product::issue_read, and tests/issue_read_cli.rs holds the controls of the two commands. The issue read guide gives their output.

tests/issue_demo.rs runs the walk-through of the issue guide on the real gos binary. Its ignored test reads the demo repository with stock Fossil and checks that Gossil refuses a copy after fossil rebuild. It then makes a clone with stock Fossil, pushes the demo repository to it, and checks that verify, a commit and task create still pass. just issue-demo runs that part with the pinned Fossil 2.29.

The module vcs_verify runs vcs verify. It runs the full proof of a repository, or the proof of one issue, and changes nothing. The proofs are LocalOwnerRepository::verify and verify_issue in storage::repository::verification. tests/vcs_verify_cli.rs holds the controls of the command.

The focused CLI controls are in tests/vcs_init_cli.rs; parser, environment, password and receipt controls are in the private vcs_init module. Source edits and authored tests do not establish a passing qualification run. Versioned executable and matching documentation delivery have their own qualification checks.

The source vcs open adapter adds first registration, reopen and bounded locator recovery without project initialization. Its configuration comes from the invocation directory, independently of an explicit root. The CLI contract covers selection, conflicts and publication phases. Scope selection and private recording are available through the library and the separate CLI checkpoint described below.

Locator/parser/publication controls are in src/checkout_locator.rs, configuration controls in src/checkout_config.rs, and executable controls in tests/vcs_open_cli.rs. Generic lifecycle commit-failure composition remains distinct from an injected native-registration COMMIT failure. Source controls and focused passes do not establish full coverage, Linux qualification or delivery.
